# Internationalisation in tom_forge_modules

The rules are the workspace guideline **`i18n.md`** (the workspace folder's
`_agent_guidelines/i18n.md`; read it with `tomAi_readGlobalGuideline`): one
`lib/resources/<package-name>_<language>.json` per package as the only place
a text is written, ids `<section>.<sub-section>.<screenElement>` relative to
the package, resolved under the scope a component is constructed in,
screen-element type suffixes with their keys, `tom_flutter_ui` components for
every widget that shows text, the tests and the coverage check, the
application's assembled resource file, and a worked example. Its sections are
cited below as § 1 … § 11.

This page holds only what is Forge's own.

## Texts outside widgets: `ForgeText` and `ForgeTextScope`

The workspace guideline (§ 5) lets a package family have a local abstraction
for texts outside widgets. Forge's is:

- **`ForgeText.id(id, params: {...})`** (`tom_forge_core`, pure Dart,
  re-exported by `tom_forge_kit`) is the **text reference**: an id relative
  to its package (the element's path with its key,
  `actions.saveAction.label`) and named parameters (`{name}`, § 6); a
  parameter may itself be a `ForgeText`. It holds no English: the text is in
  the package's resource file. `ForgeText.literal(text)` marks a runtime text
  that nothing looks up (§ 9): a file name, a font's name, a choice a
  provider answers. Everything a kit type shows that is not a widget is a
  `ForgeText`: an action's title, a configuration description's titles,
  labels and help texts, a status message, a notification, the user message
  of an exception. (`ForgeText(key, fallback)`, an absolute key with an
  English fallback, is the form of the packages not migrated yet.)
- **`ForgeTextScope`** (`tom_forge_kit`) is the resolver: it captures
  `TomScope.current` when it is constructed; `resolve(ForgeText)` reads
  `<scope path>.<id>` from the application's `TomTextResourceProvider` and
  fills the parameters, `text(id, params: {...})` does the same for an id
  written in place. An id nothing resolves shows its full path. A key with a
  fallback is tried under the scope, then alone, then the fallback is shown,
  so unmigrated texts read as before. `ForgeTextScope.root` reads ids as they
  are written.
- **A module carries the text scope it was constructed in**
  (`ForgeKitModule.textScope`). An application constructs a module inside the
  scope it mounts the module's package under (§ 8); the kit hands the scope
  on:
  - **actions:** an action gets its label as `title: ForgeText.id(...)`;
    `ForgeAction.label` resolves it with the action's `textResolver`. The
    module may pass `textResolver: textScope` itself; the kit binds every
    module action with a title and no resolver to its module's scope when it
    registers it and when a host lists a module's actions
    (`forgeModuleActions(module)`), so the shell's menus, the command palette
    and quick open show the module's wording;
  - **configuration descriptions:** `forgeConfigurationTextScopesOf(api)` maps
    each contributed description to its module's scope; the application
    hands the map to its `ForgeConfigurationValues` (`textScopes`), and each
    tile reads its section under `values.textScopeOf(descriptionId)`. The
    panel shell does both;
  - **notifications:** `notifications.showErrorText(textScope, message,
    actions: [...])` (and `showInformationText`, `showWarningText`) resolve
    the message and the action labels under the scope and answer the chosen
    action as its `ForgeText`.

  A service or controller that words messages itself holds a
  `ForgeTextScope` of its own, constructed in its component's scope.
- **Pure-Dart packages without Tom Core** (`tom_forge_core`,
  `tom_website_editor_core`) only build `ForgeText`s (or, where they must not
  depend on `tom_forge_core`, an id and a parameter map their Forge adapter
  turns into one); they never resolve. `ForgeTextResolver` (`tom_forge_core`)
  is the interface a type below the kit holds its resolver as.

## Widgets

- Forge's shared widgets (`tom_forge_shared_ui`) and the shell's own widgets
  take a `tomId` as § 4.4 says. `tom_forge_shared_ui` is a widget library in
  the sense of § 4.5: its fixed wordings are in its own file, read override
  first, and an application mounts it under `tom_forge_shared_ui`.
- A widget that shows a `ForgeText` it was handed resolves it in its build,
  not at construction, so a new language shows after a rebuild, under the
  owner's scope: `ForgeTextScopeWidget` (`tom_forge_kit`) puts a scope above
  a subtree and `ForgeTextScopeWidget.of(context).resolve(text)` reads it
  below (the configuration tile puts its description's scope above its
  editors; `ForgeConfigurationLabels.resolveIn(context, text)` reads it). A
  dialog or sheet opened from such a subtree keeps the scope with
  `builder: ForgeTextScopeWidget.keep(context, (context) => ...)`.

## Tests

The shared test support of § 7 is `tom_text_testing` (Tom Core repository,
pure Dart). A package of this repository with texts adds it as a dev
dependency:

```yaml
dev_dependencies:
  tom_text_testing:
    path: ../../core/tom_text_testing
```

and one test file, `test/i18n_coverage_test.dart`, which names Forge's text
references as id carriers and `ForgeText.literal` as a call whose text is no
resource:

```dart
import 'package:flutter_test/flutter_test.dart'; // test in a pure-Dart package
import 'package:tom_text_testing/tom_text_testing.dart';

void main() {
  test('texts and code agree', () {
    expectTextCoverage(
      'tom_forge_quick_open',
      carriers: const [
        TextIdCarrier.call(
          r'\bForgeText\.id',
          includesKey: true,
          paramsArgument: 'params',
        ),
        TextIdCarrier.call(
          r'\b[tT]extScope\.text',
          includesKey: true,
          paramsArgument: 'params',
        ),
      ],
      nonUserCalls: const [r'^ForgeText\.literal$'],
    );
  });
}
```

A `ForgeText` that still passes an English fallback fails it as a
user-visible literal. Widget tests load the package's texts with
`PackageTexts.load('<package>')..install()` and construct the component (or
its module) in `texts.run(...)`; `clearTexts` goes into `tearDown`.

## Which package is migrated where

`_ai/quests/tom_forge/tom_forge_i18n.md` lists every package of this
repository and of `tom_forge` with the todo that migrates it and its state.
Packages hosted from `tom_modules` or Tom Core that still show English
literals are not migrated in a Forge todo: a todo is filed in the quest that
owns them.
