# Internationalisation in tom_forge_modules

The rules are the workspace guideline **`i18n.md`** (the workspace folder's
`_agent_guidelines/i18n.md`; read it with `tomAi_readGlobalGuideline`): one
`lib/resources/<package-name>_<language>.json` per package as the only place
a text is written, ids `<section>.<sub-section>.<screenElement>` relative to
the package, resolved under the scope a component is constructed in,
screen-element type suffixes with their keys, `tom_flutter_ui` components for
every widget that shows text, the tests and the coverage check, the
application's assembled resource file, and a worked example. Its sections are
cited below as § 1 … § 11.

This page holds only what is Forge's own.

## Texts outside widgets: `ForgeText` and `ForgeTextScope`

The workspace guideline (§ 5) lets a package family have a local abstraction
for texts outside widgets. Forge's is:

- **`ForgeText`** (`tom_forge_core`, pure Dart) is the **text reference**: an
  id relative to its package and named parameters (`{name}`, § 6); a
  parameter may itself be a `ForgeText`. `ForgeText.literal(text)` marks a
  runtime text that nothing looks up (§ 9): a file name, a font's name, a
  choice a provider answers. Everything a kit type shows that is not a widget
  is a `ForgeText`: an action's label and tooltip, a configuration
  description's titles, labels and help texts, a status message, a
  notification, the user message of an exception.
- **A `ForgeText` holds no English.** The text is in the package's resource
  file; the id is the element's path with its key
  (`actions.saveAction.label`).
- **`ForgeTextScope`** (`tom_forge_kit`) is the resolver: it captures
  `TomScope.current` when it is constructed, and `resolve(ForgeText)` reads
  `<scope path>.<id>` from the application's `TomTextResourceProvider` and
  fills the parameters; `text(id, {params})` does the same for an id written
  in place. A missing text shows its path.
- **A module carries the text scope it was constructed in.** An application
  constructs a module inside the scope it mounts the module's package under
  (§ 8); the kit keeps that scope with the module, and whatever shows a
  module's `ForgeText`s — the shell's menus and command palette, the
  configuration tiles of `tom_configuration_ui`, notifications — resolves
  them with the owning module's scope. A service or controller that words
  messages itself holds a `ForgeTextScope` of its own.
- **Pure-Dart packages without Tom Core** (`tom_forge_core`,
  `tom_website_editor_core`) only build `ForgeText`s (or, where they must not
  depend on `tom_forge_core`, an id and a parameter map their Forge adapter
  turns into one); they never resolve.

## Widgets

- Forge's shared widgets (`tom_forge_shared_ui`) and the shell's own widgets
  take a `tomId` as § 4.4 says. `tom_forge_shared_ui` is a widget library in
  the sense of § 4.5: its fixed wordings are in its own file, read override
  first, and an application mounts it under `tom_forge_shared_ui`.
- A widget that shows a `ForgeText` it was handed (a configuration tile, a
  menu entry built from an action) resolves it with the owner's
  `ForgeTextScope` in its build, not at construction, so a new language shows
  after a rebuild.

## Tests

The shared test support of § 7 is `tom_text_testing` (Tom Core repository,
pure Dart), a dev dependency of every package of this repository that has
texts. A Forge package's `test/i18n_coverage_test.dart` calls its coverage
check with `ForgeText` named as an id-carrying type, so a `ForgeText` whose
id is not in the file, or that still passes an English fallback, fails it.

## Which package is migrated where

`_ai/quests/tom_forge/tom_forge_i18n.md` lists every package of this
repository and of `tom_forge` with the todo that migrates it and its state.
Packages hosted from `tom_modules` or Tom Core that still show English
literals are not migrated in a Forge todo: a todo is filed in the quest that
owns them.
