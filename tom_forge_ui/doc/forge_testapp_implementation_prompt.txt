Implement Tom Forge UI Test Application -- Complete Implementation

CONTEXT

Build a minimal demo IDE test application in tom_forge_ui_test that exercises the
complete tom_forge_ui shell interface stack. The app uses an in-memory file system,
concrete shell implementations, and wires up all three editor adapters (Markdown,
Dart, YAML) with five views (Explorer, Problems, Output, Search, Outline).

Read these documents fully before starting:
- Specification: tom_forge/tom_forge_ui/doc/tom_forge_ui_testapp.md
- Concept doc: tom_forge/tom_forge_ui/doc/forge_panel_shell_concept.md
- Impl spec: tom_forge/tom_forge_ui/doc/forge_panel_shell_spec.md

IMPLEMENTATION TASKS
========================================================================

Phase 1: Core Shell Wiring (8 files)

1. Create src/sample/workspace_seed.dart
   Constants for sample file contents. 7 files total:
   - /README.md (~40 lines markdown with headings, lists, code blocks)
   - /pubspec.yaml (standard Dart pubspec)
   - /lib/main.dart (~30 lines with main(), imports, runApp)
   - /lib/src/app.dart (~50 lines with StatelessWidget class)
   - /lib/src/utils.dart (~25 lines with utility functions)
   - /test/app_test.dart (~20 lines with test group)
   - /doc/architecture.md (~30 lines markdown with headings)
   Provide a Map<String, String> constant mapping paths to contents.
   Keep total content under 200 lines.

2. Create src/services/memory_file_system.dart
   Concrete ForgeFileSystem backed by Map<String, List<int>>.
   IMPORTANT: ForgeFileSystem imports dart:io (FileStat, FileSystemEntity,
   FileSystemEvent). Since this is an in-memory FS, you have two options:
   a) Return real FileStat/FileSystemEntity objects where possible (using
      memory-backed stubs), or
   b) Provide a MemoryFileStat class and override only the stat() return.
   The list() method can return empty list for directories or create
   lightweight entities. The watch() method returns an empty stream.
   The important methods are read/readBytes/write/save/delete/exists.
   Seed from workspace_seed.dart on construction.
   Fire onDidChange/onDidSave streams appropriately.

3. Create src/shell/test_system_state.dart
   Concrete ForgeSystemState. Use ValueNotifier internally for mutable state.
   Use StreamController.broadcast() for all event streams.
   Start with sensible defaults (empty lists, null where appropriate).
   Create a ForgeApplication with title "Forge Test IDE".
   Methods to update state should be callable from TestLayoutController
   and other services.

4. Create src/shell/test_layout_controller.dart
   Concrete ForgeLayoutController with:
   - Panel visibility and size state via ValueNotifiers
   - MiddlePanelState and OpenEditorTab internal classes
   - openFile(uri) resolves editor by extension, loads content from
     MemoryFileSystem, creates controller, creates adapter, adds tab
   - Needs reference to TestSystemState to update activeEditor/openEditors
   - Needs reference to MemoryFileSystem to read file content
   - Needs reference to registered modules (via ForgeModuleRegistry) to
     find editors that canHandle the URI
   Defaults: leftPanel=250px visible, rightPanel=220px visible,
   bottomPanel=180px visible, 1 middle panel.

5. Create src/shell/test_module_registry.dart
   Simple Map<Type, ForgeModule> backing.

6. Create src/shell/test_status_bar.dart
   Collects StatusBarItem instances from registered modules.

7. Create src/shell/test_shell_api.dart
   Concrete ForgeShellApi aggregating all services.
   Constructor takes all service instances.

8. Create src/app.dart
   ForgeTestApp StatelessWidget wrapping MaterialApp with dark theme.
   Home widget is ShellScaffold (created in Phase 2).

9. Create/update main.dart
   Wiring sequence:
   a) Create MemoryFileSystem and seed with workspace_seed
   b) Create all service instances (diagnostic, output, search, etc.)
   c) Create TestSystemState
   d) Create TestLayoutController (needs systemState, fileSystem, modules ref)

========================================================================
MEMORY FILE SYSTEM IMPLEMENTATION GUIDANCE
========================================================================

The ForgeFileSystem interface imports dart:io types. For the in-memory
implementation:

1. Store files as Map<String, List<int>> (path -> bytes)
2. Store directories implicitly from file paths
3. For read(uri) -> decode bytes to string
4. For write(uri, content) -> encode string to bytes, store
5. For stat(uri) -> This is complex because it returns dart:io FileStat.
   Create a helper that returns FileStat using FileStat.statSync on a temp
   path, or return a mock. Simplest: skip full stat support and return
   a minimal FileStat-like if the platform allows constructing one.
   Alternative: change the method signature awareness -- the test app is
   the consumer, so if stat() throws UnsupportedError, the views can
   handle it gracefully.
6. For list(uri) -> Return a list of child paths as simple objects.
   Again, FileSystemEntity is from dart:io. Build a shim or return
   lightweight wrappers.
7. For watch(uri) -> Return Stream.empty()
8. For applyWorkspaceEdit -> Apply text edits and file operations to the
   in-memory map.

Pragmatic approach: The MemoryFileSystem is only used by our own views and
layout controller. Views call read/write/exists/list. They do NOT need real
FileStat or FileSystemEntity objects. So:
- Implement a MemoryFileStat and MemoryFileSystemEntity if needed
- Or have the file explorer just call a custom listFiles() method
  on MemoryFileSystem that returns List<MemoryFileEntry> instead,
  and have that be the working API for the explorer view.

The test app is a self-contained demo. The abstract interface is the
contract for production use. The test app can work around dart:io
limitations pragmatically.

EDITOR CREATION PATTERN
========================================================================

When opening a file, the layout controller creates editor instances:

For .md files:
  final controller = MdEditorController();
  controller.markdown = fileContent;
  // controller.uri = uri;  // if MdEditorController supports it
  final editor = ForgeMdEditor(
    controller: controller,
    module: shellModule,  // TomForgeShellModule instance
  );

For .dart files:
  final controller = DartCodeController();
  controller.userCode = fileContent;
  // controller.uri = uri;  // if DartCodeController supports it
  final editor = ForgeDartEditor(
    controller: controller,
    module: shellModule,
  );

For .yaml files:
  final controller = YamlEditorController();
  controller.yaml = fileContent;
  // controller.uri = uri;  // if YamlEditorController supports it
  final editor = ForgeYamlEditor(
    controller: controller,
    module: shellModule,
  );

Check each editor controller's API for the exact way to set initial content
and URI. The adapters reference controller.uri, controller.markdown,
controller.userCode, etc. Match those APIs.

    final minutes = duration.inMinutes.remainder(60);
    final seconds = duration.inSeconds.remainder(60);
    return '${hours}h ${minutes}m ${seconds}s';
